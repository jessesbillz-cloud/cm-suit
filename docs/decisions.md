# Decisions

Short entries, newest first. One line on what, one on why.

- **2026-09-26 — Repo name `cm-suit`, project codename `cm-suite`.** The product name is undecided (`FUTURE_NAME`); the repo name is throwaway and doesn't appear in the product.
- **2026-09-26 — Staging Supabase project `cm-suite-staging` in Jesse's Pro org, us-west-1.** Production is created at first promotion, same org.
- **2026-09-26 — pgmq lives in schema `queue`, wrapped by `public.enqueue_job`.** `pgmq` and `pgmq_public` are never exposed to PostgREST.
- **2026-09-26 — Access links carry an opaque 32-byte token; only its SHA-256 is stored.** A leaked database dump can't be replayed into a session.
- **2026-09-26 — Rate limits live in `public.rate_limits` (token bucket per key), checked by `_shared/ratelimit.ts`.** One implementation for all public endpoints.
- **2026-09-27 — Staging is hosted on GitHub Pages (like My Daily Reports), not Cloudflare Pages.** Jesse's rule: use the services he already has. Workflow `deploy-pages.yml`; URL https://jessesbillz-cloud.github.io/cm-suit/ (sub-path, so `BASE_PATH` and `APP_BASE_PATH`). Cloudflare Pages/R2 and Fly stay in SPEC as options, not requirements, until Jesse says otherwise.
- **2026-09-27 — Email provider is Resend (MDR already uses it), not Postmark.** `_shared/email.ts`, the two webhooks and the Auth SMTP settings move to Resend. The domain question (SPEC §16 Q2) is unchanged.
- **2026-09-27 — Railway is not used.** Jesse's Railway trial has ended; nothing there.

- **2026-09-27 — Companies and jobs are created in the app through `create_org` / `create_project` (migrations 0013-0014).** Invoker rights, so RLS stays the gate; the database makes the id and a repeat returns the first row. No more SQL seeding.
- **2026-09-27 — People may set only a job's and a company's own columns (column grants).** `org_id`, `created_by`, intake/inbound addresses and tokens are written by triggers, RPCs or the service role only.
- **2026-09-27 — Sealed bids are locked once a bid is in.** A signed-in person can't lift the seal or pull bid time earlier until bid time; otherwise the seal would be one checkbox away from peeking.
- **2026-09-27 — Job modules gate the rail: Bids, Files, Calendar.** Board, People and Settings are always on. New jobs start with all three; jobs with none were given all three.
- **2026-09-27 — A membership row's company must be its job's company (composite foreign key, migration 0015).** The member policies trust `is_org_admin(org_id)`; without the key, anyone could make a company and write themselves into another company's job. Found by an independent review of 0013.
- **2026-09-27 — `submit_bid` holds the job row while recording a bid.** Lifting a seal waits for an in-flight bid, and the seal guard then sees it.
- **2026-09-27 — Sign-in allowlist (migration 0016).** Jesse: only his two addresses sign in to staging. The list is data on staging (`signin_allowlist`); an empty list means no limit, so outside people work again once it's emptied or they're added. The sign-in email box no longer invites the browser's saved addresses.
- **2026-09-27 — Bids are read without the worker.** `extract-bid` reads a PDF (unpdf, the serverless pdf.js), `.eml` or `.txt` itself when the worker has not written `file_pages`, stores the pages once, and marks Word/Excel/images and scans `text_status` none ("Can't read": open the file). The office drops a folder of bids into the Received view; the package comes from the leading CSI division in the file name, the sub link from the bidder name after reading.
- **2026-09-27 — The sub directory is used by whoever holds `bids.manage` on one of the org's jobs, or an org admin (`can_manage_subs`, migration 0018).** SPEC §5.2 puts "directory use" under `bids.manage`; before, only org members could read it (an estimator added to a job is not one) and any org member could write it. The CSLB result is recorded through `record_cslb_check` so its time is the server's.
- **2026-09-27 — Master sub lists are imported server-side (`import-subs`, ExcelJS `npm:exceljs@4.4.0` for .xlsx, a small CSV parser for .csv).** The file is grouped per company in the function and merged by `import_subs` as the caller: trades unioned, contacts merged, empty fields filled, nothing wiped, safe to repeat.
- **2026-09-27 — Official PDFs are rendered by edge functions, not the worker.** No worker host runs (Fly isn't used), so the pure builders and the one signature stamp live in `supabase/functions/_shared/pdf/` (pdf-lib, in the functions' import map; the app no longer depends on it) and server-made PDFs are stored through `_shared/generatedPdf.ts` as clean files with their sha256. A hosted worker would import the same files.
- **2026-09-27 — One calendar table (`calendar_entries`, migration 0021).** Modules mirror their rows into it from their own triggers (`calendar_mirror`, not user-callable) and each line carries the capability that may read it, so "All my jobs" is one query. New capabilities: `calendar.read` (every role but bidder) and `calendar.manage` (project admin, estimator, PM, PE, super, inspector). A job moved to construction gets Dailies, Inspections, Deliveries and Corrections on its rail.
- **2026-09-27 — Inspection requests (migration 0024) are written only through RPCs that run as the caller.** The IR number comes from `next_number(project, 'ir')` at submit (there are no drafts, so it is the one number an IR has); every change lands in `ir_events` from a trigger; requesters see other people's requests only through `ir_calendar` (day, time, length, type, color). The first inspector to act owns a request; a helper reports, the owner decides, generates and sends. New capabilities: `ir.gc_approve` (project admin, PM, super) and `ir.view_all` (project admin, PM, PE, super, inspector, owner rep).
- **2026-09-27 — The IR on file is always server-made, and "results sent" always means an email went.** `ir_attach_pdf` and `ir_mark_sent` are service-role only, reached through `ir-pdf` / `ir-send` after the caller-run checks. IR PDFs live in Reports / Inspection reports (read: `ir.view_all`, `ir.decide`); a requester reaches their own IR, attachments and result photos through `authorize_ir_file` (request-scoped, scan rules kept, logged). Request files must sit in the job's "Inspection requests" folder (requesters write, can't read others'), so a request can't hand out a file from any other folder.
- **2026-09-27 — Deliveries (migration 0025): every write is an RPC and the database decides Standby.** An overlap is never refused; the post lands as Standby (again when an edit moves the time). Receipt numbers use the SPEC §5.3 kind `delivery`. The company list is the job's own names (`delivery_companies`, "Other" adds one for everyone) plus the companies of members who can post, most-used first. New capabilities: `deliveries.view` (every role but bidder), `deliveries.post` (project admin, PM, PE, super, foreman, sub).
- **2026-09-27 — The delivery link stores only the token's sha256 and shows the link once.** "New link" locks the old one out at once and can be undone for 15 minutes by the person who made it. The link can view the board, post with a typed name and fetch its own receipt; no edit, delete or photos from the link.
- **2026-09-27 — Default folders follow the company kind and DSA (migration 0027, `folder_templates`, data not code).** Jesse: a job opens with what that kind of user uses most. Inspectors: Plans, Specs, then DSA 103 and CCDs on DSA jobs (`projects.is_dsa`) or Testing & inspections on other jobs, Reports, Photos. GCs: Plans, Specs, Bids received, Reports, Photos. Everyone else: Plans, Specs, Reports, Photos. Turning DSA on adds the DSA folders once; nothing is ever deleted. "Inbound" is no longer made (existing ones are "Emailed in", hidden while empty). A non-GC job gets Bids received with its first bid package.
- **2026-09-27 — Folders carry `ai_reads` ("Search and AI read this").** Jesse: rather than guess, let people add folders and say whether what's in them matters to everything else. On by default; off for Photos, Bids received (money stays out of general search) and Emailed in. Stored and shown now; search and the AI honor it when they arrive.
- **2026-09-27 — Photos open before a virus scan (authorize_download).** No scanner runs yet, so every file stays pending; field photos must be visible to the team, and photos taken in the app are re-encoded on the phone. A pending file whose type and name are both an image (JPEG, PNG, WebP, HEIC/HEIF) opens for the folder's readers. Everything else stays uploader-only until a scanner is chosen; infected is always refused.
- **2026-09-27 — Look: IBM Plex Sans, self-hosted; cards with a hairline edge and a two-step shadow, headers on a faint tint.** Jesse: "more rich and defined shadows and boxes... the font is very basic." Plex Sans (SIL OFL) is made for interfaces at small sizes and reads as technical, which suits inspection work. Latin-1 subset, weights 400/500/600, from IBM's release, in `public/fonts` with its license.
- **2026-09-27 — No public function takes a table's row as its only argument (migration 0028).** PostgREST treats such a function as a computed column: it shows up as a readable field in the API and the CLI type generator adds it to the table's Row type. Helpers take ids; `22_no_row_helpers.sql` keeps new ones out.
- **2026-09-27 — IR results go on the inspector's daily for the inspection date (migration 0029).** Written when the IR PDF is made, updated in place when it is remade, taken off when the PDF is deleted, moved with the date. Only for inspectors who write dailies on the job; a deleted report stays deleted.
- **2026-09-27 — Security review of 0021-0029 fixed (migration 0030).** Signing (`ir_sign`, `begin_daily_submit`) checks the fresh sign-in in the database too (the JWT's `amr` time, 5 minutes); an IR re-signed after its PDF was made is marked stale and can't be re-stamped. People can't make folders of a system kind or take the system folder names, so bids can't be steered into an open "Bids received"; folder parents stay in the job and never loop. Daily setup settings are bounded in the database; "Send to team" is limited to 10 an hour per person and 3 per report.
- **2026-09-28 — The app opens on "All my jobs" (desktop and phone).** Jesse: that's where the board shows what needs you across every job, so you pick where to go first. On All my jobs the rail shows only the cross-job tools (Board, Bids, Calendar; `ALL_JOBS_TOOLS` in lib/jobs.ts); Bids there is a pipeline of the jobs you bid (`bid_pipeline()`, migration 0032, counts only), and job tools appear once a job is picked.
- **2026-09-28 — An opened board line shows the thing it's about, with its actions (Download, Open), never the line again.** One mapping from a record type to the tool that owns it (lib/entityTarget.ts) serves the board and the calendar. With nothing open beside the board, the right column shows Today.
- **2026-09-28 — A CSI MasterFormat reference seeds package numbering (migration 0033).** All 50 divisions and 254 common sections (2016-2020 numbering, each checked against CSI's published lists), not the whole MasterFormat (CSI's licensed work); the estimator's own list imports later (SPEC §11.2). Packages carry `spec_sections`; any 'NN NN NN' number is allowed so org sections can be added.
- **2026-09-28 — Required bid forms per job (migration 0034).** A 15-form default list for California public works (with the bid / after award, each with its code section), made per job the first time a bids manager opens Bids, filtered by prevailing wage and DSA. Files go to a per-job "Bid forms" folder only bids.manage can open (the filled bid form carries the price). The list is a draft for Matt and Jesse to confirm (SPEC §16 Q3).
- **2026-09-28 — Company invites by email (migration 0035).** `org_invites` binds on the person's first sign-in through `accept_invites`, like job invites, so a company can be set up for someone before they log in. Only an owner hands out ownership. On staging, Matt is invited as owner of Lulling Construction and as project admin on the Hunter Hall sandbox, next to his existing invite on the Rancho San Antonio job.

- **2026-09-28 — Testing login: personal sign-in links, no codes (migration 0036, `key-login`).** Jesse: "turn the code thing off while we test; only me and Matt have access; re-implement the safeguards at the end." `/k/<key>` signs its owner in with no email and no code (the key's SHA-256 in `signin_keys`, allowlisted addresses only, revocable). Switch `security_switches.testing_relaxed_login` (off by default; on in staging now) skips the re-confirmation to sign and the two-step for pricing. **To restore the safeguards:** set the switch off, revoke every `signin_keys` row, delete `key-login` and the `/k/` route, and drop it from config.toml, the probes and the service-key allowlist.
- **2026-09-28 — Testing: uploads usable without a virus scan (migration 0037).** No scanner runs yet, so uploads sat on "Scanning". Switch `security_switches.testing_skip_virus_scan` (off by default; on in staging now) marks a finished upload clean and sets `files.scan_skipped_at`. **To restore:** switch it off, set `scan_status = 'pending'` where `scan_skipped_at` is set, and run the worker; the queued scan jobs scan them.
- **2026-09-28 — RFIs move along a route the job sets, and get their number only at issue (migration 0038, `rfis` function).** Originator signs and sends, each reviewer on the job's route (a role on the job, or one person; the RFI keeps its own copy from its first send) edits and sends it on or back, a PM / PE signs and issues (`next_number(project, 'rfi')` there), the architect answers, the originator has the job's impact window to claim cost or time (permanent). Why: Jesse wants Procore-easy RFIs where each person reads, agrees or fixes, and moves it on in the app, with no downloading and emailing, and a draft or a sent-back RFI never burns a number.
- **2026-09-28 — Testing: "View as" in the top bar (migration 0039).** Jesse's account takes any role on every job he's on (architect, sub, PE, …) from a drop-down, and "Me" puts his real roles back, so he tests every side without extra accounts. Only testers listed in `testing_superusers` (set by hand on staging) while `security_switches.testing_view_as` is on. **To remove:** pick "Me", switch it off, drop `testing_superusers`, `testing_role_home` and the two functions, delete `ui/ViewAs.tsx` and `data/viewAs.ts`.
- **2026-09-28 — My Daily Reports stays live for Jesse's two jobs; the suite is built alongside it.** People already use MDR on their phones, so nobody moves until the suite does everything they need there.
- **2026-09-28 — The rail is lean and follows your position; counts show what needs you (migration 0040).** Jesse: "I don't want to clutter the job … we have our recommendations based on the type of position you have." Each role's rail is data (`roles.recommended_tools`, a few tools, Board first; `my_recommended_tools` minus the job's switched-off tools); pins in Settings win on every job (`user_layout.rail_items`, null = recommended; all rows reset). The job's other tools sit under one More item (desktop menu, phone sheet), so each tool keeps one way in. A badge counts my open tasks per record type (tool from lib/entityTarget) plus the RFIs I'm waiting on (`my_tool_counts`, run as the caller); anything with no place on the rail counts on the Board.
- **2026-09-28 — Company forms for dailies; the VIS daily report is the first (migration 0041).** Jesse: "re-create Hunter Hall here." Which form is data: `orgs.settings.report_generator` names a job's default, and each person writes the form of the setup they chose last (`daily_setups.report_type`, `choose_daily_form`). A form's fields live in `_shared/reportForms.ts` (job values typed once in Setup, the day's values on the report); its PDF is a pure builder (`_shared/pdf/vis.ts`, MDR's coordinates) with the company's logo (`orgs.logo_path`) and footer (a job value), so nothing about the company is in code. Each form numbers on its own, so "Next number" continues MDR's sequence. Kept from MDR's real output: no bullets in IOR Notes (its text cleaner blanked them), ALL-CAPS or **bold** lines as headers (without its looser rule that bolded "CEMEX delivered ...").
- **2026-09-28 — Hours, timesheets and invoices are the person's own (migration 0043, `timesheets` function).** A report's hours (`daily_reports.hours`) are set only by its author, on a submitted report, and don't make a signed report "Changed". Contract hours (`job_hours_budgets`), billing details and rates (`billing_profiles`, `billing_job_rates`) and invoices are readable by their owner only (RLS `user_id = auth.uid()`, no capability), so no admin or PM ever sees a person's rate; their audit lines carry no project and no amounts. Invoice numbers come from the person's own counter (settable forward), one invoice a month, so asking again never burns a number (MDR's hand-fixed counter). Timesheet and invoice PDFs are rendered by the function from saved data on each request and handed back to the one person who asked, not stored, so there is no file anyone else could reach; the timesheet is signed (fresh sign-in, content hash in the audit log). The Hours tool is on for inspector companies' jobs and recommended to inspectors, special inspectors and project admins (an inspector company's job is made by its inspector; a job without Hours drops it); Timesheets shows on All my jobs for people whose position keeps hours on some job.
- **2026-09-28 — The inspector who runs the job (migration 0044).** Jesse: an inspector uses the app for all their daily reports and scheduling the way they use MDR today: they make their own jobs and run them. One person holds one role per job, so a new role, `inspector_admin` ("Inspector who runs the job"), holds the inspector's and the project admin's capabilities except `bids.*` (no bid management, pricing or findings on an inspector's job), with the inspector's rail; it is data like every role. The creator of a job in an inspector company gets it (`tg_project_created`); every other company kind still makes project_admin. Existing inspector-company jobs moved their creator over (`inspector_admin_backfill`, owner only), including a tester's real role kept aside by View as.
- **2026-09-29 — Inspector-only tools stay in My Daily Reports; what comes over is for everyone.** Jesse: "I never really use the inspector tools … make a generalized tool so it'll be for everyone." Not carried over: inspection cards and trackers, the UL and framing checklists, the correction-notice readers. Carried over and open to any role by capability: daily reports, the calendar, scheduling requests, hours.
- **2026-09-29 — The job's request link, QR sheet and all-my-jobs link (migration 0046, `request-link`, SPEC §6.4 #4).** MDR's request page, QR sheet and hub, rewritten to these rules: `/r/<job>?t=<token>` and `/h/<hub>?t=<token>`, only token hashes stored, a new link ends the old one at once (Undo for 15 minutes on the job's link). Whoever manages the job's members makes its link; anyone who decides inspections has one link for all their jobs. A visitor proves their email with the code, then joins as a sub (never changes an existing member; a revoked one stays out) and lands on the request form. No new capabilities.
- **2026-09-29 — Photo tiles show the picture (migration 0047).** A preview asks the very gate the download of that file asks (`authorize_preview` calls `authorize_download`, `rfi_authorize_file` or `authorize_ir_file`), images only, and is not logged as a download. One hook (`data/preview.ts useImageUrl`) and one tile (`ui/Thumb`) show every photo.
- **2026-09-29 — Saving your own profile works again (migration 0048).** The profile update policy read `auth.users`, which signed-in users may not read, so every save failed. Now a person may update only the columns they own, granted by name (name, phone, title, company, time zone); email, signature file and certificates are not among them.
- **2026-09-30 — The RFI log shows where every RFI is and how long it has sat with each person (migration 0049, `rfi_progress`).** Jesse, after Procore's RFI log: "I don't like the ball in court thing … show progress, show status bar, show how long it's been in their court … we're holding everyone accountable." Each row is the number and the whole title (due date at the right, red once late), then a strip of one cell per step of that RFI's own route: done steps with a check, who and how long ("PE · 1d"), the step that has it now filled in the accent ("Architect · 5d"), steps ahead as outlines, the end green. This replaces CLAUDE.md's "no ball-in-court or days-open columns" for RFIs: who has it is in the strip, not a text column, and the log has no columns, View buttons or sorting by header. Days are whole days on the job's clock, computed by the server from the RFI and its events (under 24 hours is "<1d", else the calendar days between in the job's zone), counting only the current pass after a "Send back". `rfi_progress` returns exactly the RFIs `rfi_list` lets the caller see (`rfi_may_see`). A tap opens the RFI in the right column with the substance at once (question, photos, the answer right under it) and three header actions: its own window, download the PDF, and full screen in the browser's own PDF viewer (the `rfis` function's `view` action, a fresh signed URL without the download header; no PDF library). History shows only in the full view.
- **2026-10-01 — The rail in two parts; each job's tools are chosen under the job's name (migration 0051).** Jesse: "on the left-hand side there is more for our big general things ... if you select a job, then certain things should pop up under it ... So they would be customizable within the job." On top, always, the cross-job tools (lib/jobs `ALL_JOBS_TOOLS`: Board, Calendar, and Bids / Timesheets when they apply to me, as on All my jobs); with a job picked they act on that job (Timesheets becomes its Hours) and never repeat below. Under a divider and the job's name: the tools I chose for this job, in my order (`user_job_rail`, own rows only, only while I'm on the job; `save_job_rail` with a version check; tools checked against `job_rail_tools()`; no row or null = my position's recommendation, `my_recommended_tools`), then More for the job's other turned-on tools, then Edit (a small panel beside the rail; on the phone, "Edit tools" in More). The phone bar is Board, Calendar, then the job's first tools. Collapsed, the rail is icons only, the job's name a thin line. **The global pins (`user_layout.rail_items`, 0040) are retired**, not kept as a fallback: two places to choose the rail (Settings and the job) would break "one way to reach each thing", and a third layer between my own list and my position's would make it hard to tell why a job shows what it shows. Each person's pins were carried into a row for every job they are on, so no choice is lost; Settings > Layout no longer lists rail tools (its sketch shows the rail as the frame does), and the column stays, unread, until Jesse OKs dropping it. For the rail, a new tool (Plans, Specs, Submittals) is one entry in lib/layout `RAIL_TOOLS` and one in `job_rail_tools()`; every job's Edit list then offers it.
